# 用途编选（D 工序）界面证据

截图来自本机一次真实走查：后端跑在本地 Docker 容器里（`fangji-backend:adoption`，独立卷，端口 18090），
前端用同一份代码 `vite build` 后以 `vite preview` 提供，Playwright 驱动 Chromium 完成登录与操作。
数据是容器里的临时项目：4 条条目（已校对/校对中、已确认/待定、缺字表阻塞各一），一份来源登记，
其中 `public_display` 用途结论为「允许」、`model_training` 未登记。

## 002 previewed.png

建批后立即预览：4 条里 1 条进入本批、3 条已定不进入、0 条待处理，理由分布按数量降序列出
（缺字表待查 / 质量状态不足 / 校对状态未到）。按钮状态与批次状态一致：预览后「确认本批采用范围」才可用。

## 003 confirmed.png

确认之后：批次状态变为「已确认」，并说明导出与下游都以这份清单为准。已确认批次不能再预览、删除或改例外。

## 004 pending.png

换到 `model_training` 用途（未登记用途结论）：进入本批 0 条，1 条待处理。界面写明
「确认后导出的清单会写明 `complete: false`，不会把部分结果冒充全量」。理由分布里能看到
「该用途尚未决定」——这条不是拒绝，是未决。

## 005 exception.png

对那条未决条目处理例外：写依据后提交，批次退回草稿，需要重新预览再确认。
例外是逐条的唯一入口；批次本身仍然只是「一条」决定。

## 006 stale.png（D5.3）

已确认批次的项目里，来源的用途结论从「允许」改成「禁止」之后：批次上出现「确认之后用途权利
变过，可能需要重评」，并说明重评只追加记录。四个数仍然是确认时的 3/3/0/0——历史没有被改写。
度量卡里「需重评 1」只表示有权利事件晚于确认时间。

## 007 reevaluated.png（D5.3 + D9）

点「按当前数据重新评估」之后：提示「已追加重评记录：3/3 → 0/3，差异在「采用数量」。已确认的
数字没有改。」事件折叠区多一条 `reevaluated`，同时保留 stored 与 current 两组数；批次的
四个数一个字没动。

## 这次走查同时验证了

- 登录后路由 `/admin/projects/:id/adoption` 可达，项目页导航里有入口。
- 导出的 JSON 清单：`counts` 满足 `total = selected + excluded + pending`，默认只含进入本批的条目，
  未采用与待处理的数量写在 `omitted` 里，文件名带用途与批次 id。
- 浏览器控制台没有运行时错误。
