# OCR 选型建议书（#120 交付物 · 非约束性）

> 本文档是**非约束性**建议，实现者可提出更优方案并推翻。目的：在"选型开放"的前提下，先给一份有依据的取舍参考，作为 #121–#125 的公共提示。

## 判断准绳

本仓库已经是一台「多人独立校对 + 分歧仲裁」的机器。因此 OCR 的目标不是"绝对正确"，而是：

1. **把人工录入成本降一个数量级**；
2. **绝不在低置信处冒充高置信**（静默替换是方言 OCR 的头号风险）。

凡是能给出**每格置信度、原文坐标、可回交裁剪图**的方案，天然更容易验收。

## 候选方案对比

### 方案 1：数字原生 PDF 分流（pdftotext / pdfjs getTextContent）
- 方言生僻字表现：极好（直接取 Unicode）
- 列还原表现：好（坐标聚类）
- 部署契合度：极高（后端已 vendored pdfjs，零新依赖）
- 成本/耗时：最低
- 许可：无新增
- 置信度/坐标：坐标有、置信度无（但本就是真值）
- 建议：**首选第一步，必做**

### 方案 2：拿源文件（InDesign/LaTeX/Word）
- 方言生僻字表现：最好
- 列还原表现：最好
- 部署契合度：最高
- 成本/耗时：一次性沟通成本
- 许可：取决于来源
- 置信度/坐标：—
- 建议：强烈建议，一次沟通省半年

### 方案 3：传统 OCR + 词表约束解码（Tesseract/PaddleOCR/cnOCR）
- 方言生僻字表现：中（靠 user-words 压制静默替换）
- 列还原表现：弱（无框线场景差）
- 部署契合度：中（Python/二进制）
- 成本/耗时：低
- 许可：开源
- 置信度/坐标：部分有
- 建议：有框表格可考虑

### 方案 4：版面/表格结构模型（PP-StructureV3/Docling/Marker）
- 方言生僻字表现：中
- 列还原表现：有框表好，无框表差
- 部署契合度：中
- 成本/耗时：中
- 许可：开源
- 置信度/坐标：部分
- 建议：词典无框线场景需谨慎

### 方案 5：VLM 端到端（PaddleOCR-VL/dots.ocr/olmOCR/GLM-OCR 或云 API）
- 方言生僻字表现：中（有幻觉风险，需强制弃权）
- 列还原表现：**好**（指令即分列）
- 部署契合度：高（发 HTTPS，适合静态二进制后端）
- 成本/耗时：中（自托管要算力；云 API 按量）
- 许可：自托管开源 / 云 API 有治理顾虑
- 置信度/坐标：置信度有、坐标部分
- 建议：无框线场景的首选方向，但必须约束幻觉

### 方案 6：双引擎交叉验证 / 一致性投票
- 方言生僻字表现：高（互相纠错）
- 列还原表现：高
- 部署契合度：高（几乎不改数据模型）
- 成本/耗时：中（两倍算力）
- 许可：开源
- 置信度/坐标：天然产出置信度
- 建议：强烈推荐，与平台逻辑同构

### 方案 7：字形聚类 + 一次标注
- 方言生僻字表现：高（自造字对症）
- 列还原表现：—
- 部署契合度：高（离线脚本）
- 成本/耗时：中
- 许可：开源
- 置信度/坐标：—
- 建议：自造字出现高频时的性价比之王

### 方案 8：集外字表示（IDS + PUA + 字形图）
- 方言生僻字表现：决定能否无损
- 列还原表现：—
- 部署契合度：高（前端已有 rareCharacters.js 半套基础）
- 成本/耗时：低
- 许可：开源
- 置信度/坐标：—
- 建议：对应 #123，必做

### 方案 9：浏览器内推理（PP-OCR/Tesseract.js）
- 方言生僻字表现：中
- 列还原表现：弱
- 部署契合度：高（后端零改造、CSP 友好）
- 成本/耗时：低（6MB 模型）
- 许可：开源
- 置信度/坐标：部分
- 建议：适合当场预览几十页，不适合整本后台批处理

### 方案 10：Rust/ONNX 静态二进制
- 方言生僻字表现：中
- 列还原表现：中
- 部署契合度：高（契合 CGO_ENABLED=0 + 只读根文件系统）
- 成本/耗时：中
- 许可：开源
- 置信度/坐标：部分
- 建议：契合部署基线，但版面分析生态需自拼

## 明确建议（可推翻）

1. **第一阶段（本组当前）先做方案 1：数字原生 PDF 分流。** 本次交付的 `extract_text.py` 已验证：文读字汇 PDF 是数字原生，直接提取文本层即可，零 OCR 成本。这是整条链路上性价比最高的一步。

2. **扫描版（无文本层）主推方案 5 + 6 组合：VLM 端到端解析 + 双引擎交叉验证。** 理由是：词典页面多无框线（列靠空白分隔），传统版面模型不稳；而 VLM 的"按词头/音读/释义三列输出，读不出用占位符，不要猜"指令天然解决分列，且适合当前"静态二进制后端"（只需发 HTTPS）。双引擎交叉验证用于压制 VLM 的幻觉（静默替换），与平台已有的"多人独立校对+仲裁"逻辑同构。

3. **生僻字/集外字必须单独走方案 7 + 8**：字形聚类一次标注 + IDS/PUA/字形图三者并存，否则"自信地写错字"会污染整个数据资产。

4. **不要用 gosseract**（Go 的 Tesseract 绑定）：它需要 cgo，会破坏当前 `CGO_ENABLED=0` 的静态构建基线。

## 治理提醒

- **语料出境（云 API vs 自托管）不是技术细节，是治理决策**，请在 #113 下确认立场后再选云方案。
- 老印本的图像预处理（纠偏、二值化、放大、去透墨）常比换引擎更有效，且与任何选型正交。

## 许可边界

- Tesseract（Apache-2.0）、PaddleOCR（Apache-2.0）、ppstructure（Apache-2.0）等开源方案许可友好，可 AGPL 兼容使用。
- VLM 自托管开源（如 dots.ocr 需查各自协议）；云 API 属外部服务，需按 ASSET_BOUNDARIES.md 登记并确认数据出境立场。
- 任何新引入第三方组件，须更新 THIRD_PARTY_NOTICES.md。
