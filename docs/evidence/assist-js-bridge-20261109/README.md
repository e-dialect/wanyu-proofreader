The combined real delivery suite rejected an otherwise valid preflight with HTTP 400: `ReferenceError: $dbx is not defined at source_fidelity.js:109 eventsFor`. This was a runtime dependency defect in the delivery-only Goja instance, not an authorization refusal or an invalid fixture. The original failure log is preserved, with its hash in [validation.json](validation.json).

`newDeliveryCompletion` already bound PocketBase core objects (`Record`, `arrayOf`) and security helpers. It retains the authoritative visibility predicates, source-completion logic, transaction app, and one-VM-per-snapshot lifecycle.

The source audit found this is the only product-created Goja runtime. Verification export runs through PocketBase's registered JSVM, which already binds Core/Dbx/Security; the Go project export does not instantiate a JavaScript runtime. No broader runtime exposure or alternative visibility path was added.

The new test calls the actual `newDeliveryCompletion` bridge against a fully migrated temporary SQLite app. Before the product fix, it reproduced the same missing `$dbx` failure (package 1.171s). After the fix, the normal run passed in 1.232s and `-race` passed in 27.124s. It checks that private staging/aborted events and malformed publication-linked human events cannot fake a completed human source review; the same bridge sees a valid event inside its own transaction, loses it after rollback, and accepts it after a genuine commit. The deliberately malformed records are internal DAO fixtures used to test defensive read behavior, not product API writes.
