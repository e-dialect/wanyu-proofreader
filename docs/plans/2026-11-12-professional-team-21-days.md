## 二、优化重点与实施范围

### 1. 角色清单与首次使用流程——本轮必做

现有帮助和练习已具备内容基础，但部分操作仍依赖长篇说明和人工指路。

在项目概览增加可操作清单：

**资料准备 → 独立校对 → 仲裁与来源核验 → 编选 → 交付 → 接收回执。**

每一步显示真实状态、阻塞原因、当前处理角色和下一操作。状态从已有业务记录计算，不允许用户勾选一个框就代替来源、许可或质量判断。

具体改进：

- 校对者突出“继续任务、原文定位、字符输入、疑点反馈、提交后回看”。
- 管理者突出“导入是否完成、哪里需要判断、为何不能交付”。
- 将现有练习说明改成分步骤卡片，直接链接对应入口。
- CSV 预检先呈现数量、错误和操作入口，完整样本按需展开。
- 统一高频流程的加载、失败重试、未保存提示、焦点和返回位置。

**验收：**至少 5 名用户参与，至少 4 人无需口头指导完成对应角色任务；管理员能在 1 分钟内说明当前阻塞和下一处理人。

### 2. 统一待处理视图——本轮必做

现有首页“需要你的判断”主要围绕仲裁，跨工序事项分散。

扩展为管理员统一待办，纳入：

- 待仲裁；
- 来源问题及待核验事项；
- 待归一复核；
- 编选例外；
- 交付待回执及退回处置。

每组显示数量、最久等待时间、处理角色和可直接进入的业务页面；支持按项目和工序筛选。

第一版直接汇总现有权威记录。没有个人负责人时显示负责角色，不虚构具体责任人；读取失败显示“未更新”，不能显示为零。

**验收：**源问题处理后汇总随之变化；撤权后不可继续看到项目事项；管理员能从首页定位并关闭一次真实阻塞。

### 3. 批次质量与交付报告——本轮必做

已有字段审计、来源判断和交付记录，但还需要让负责人清楚回答：**这批资料处理了多少、验证了什么、还有哪些不能使用。**

增加可查看、可导出的批次报告，包含：

| 内容 | 明确口径 |
|---|---|
| 导入 | 声明数量、成功数量、错误与排除数量 |
| 校对 | 独立提交覆盖、完成数量、待仲裁数量 |
| 质量 | 来源正确、错误、未核实及抽检范围 |
| 编选 | 采用、排除、待定与阻塞原因 |
| 交付 | 包版本、条目数量、摘要、接收结果及冲突 |
| 效率 | 近 7 天有效完成量、仲裁和回执等待时间 |

所有指标附分母、统计时间和缺失状态。历史没有采集的数据保持未知，不补造耗时或失败次数。

同时建立真实试点：

- **莆仙至少 300 条**，覆盖常见条目、音标、声调、难字及分歧案例，完成两人独立校对和真实接收。
- 从流程完成结果中**分层抽检至少 100 条**，覆盖一致通过与仲裁通过；高风险字符另做定向核验。
- **蒙古语至少 100 条补充样本**，重点核验输入、组合字符、显示、复制及导出；复用既有大规模导入结论。
- 抽检记录范围、抽样方法、专家判断和错误类型。流程一致率、来源正确率、抽样错误率分别报告。
- 真实接收方完成一次正常接收、一次部分冲突和一次更正版处理；异常演练使用隔离副本。

**验收：**报告可按批次和版本复算；已发现的重大错误全部修复或明确隔离；下载成功与接收成功分别记录；旧交付包和历史回执保持不变。

### 4. 运行保障与版本治理——本轮必做，按资源分别验收

| 领域 | 本轮动作 | 完成证据 |
|---|---|---|
| 版本与文档 | 建立唯一能力状态表，区分代码、自动化、真人、生产启用和接收方验收；修复运行版本 `unknown` | 页面、镜像、功能开关与文档能相互核对 |
| 账户安全 | 验证改密、全设备退出、撤权、附件权限及管理员恢复；已有 SMTP 可用时完成真实邮件测试 | 实际成功与失败场景回执 |
| 备份恢复 | 核查现有调度，完成整目录备份及隔离恢复；已有异地位置可用时验证加密副本 | 附件摘要及登录、校对、仲裁、导出对账 |
| 监控告警 | 复用现有监控，关注请求失败、作业积压、磁盘、内存、备份年龄 | 模拟异常能被发现，已有渠道可用时验证通知触达 |
| 性能 | 在现有隔离资源运行真实混合负载，按测量结果修复瓶颈 | 保存版本、负载、延迟、资源、失败和数据对账 |

## 三、接口、数据与兼容约束

本轮新增能力尽量采用只读汇总和现有流程组合：

- 新增工作台待办汇总接口，返回授权项目内的工序、数量、等待时间、处理角色及业务定位信息；采用服务端分页和聚合，不在浏览器拉全量条目。
- 新增项目批次报告接口，绑定既有批次标识和统计依据；导出复用现有作业机制，增加批次报告输出类型，提供 JSON 数据及 CSV 明细。
- 新增报告类型至少包含版本、批次、生成时间、指标分母、未知项和来源依据；来源变化后旧报告标为历史快照，不静默更新。
- 抽检清单保存抽样依据和条目标识；具体判断沿用现有来源核验、质量状态及审计流程，不增加另一套“正确答案”。
- 报告作为受保护的独立成果附件交付，不直接修改现有 Review Bundle v0 协议或旧包字节。
- 新接口沿用现有账户及项目权限；校对者不能通过汇总、报告或深链看到他人的未公开答案。
- 新迁移只追加。辅助分析新发布机制产生记录后，禁止默认切回不理解该机制的旧程序；通过关闭相关入口和前滚修复止损。

发布准备必须重新核验精确镜像、数据副本和迁移依据，不能沿用过去例外放行作为本轮验收证明。

## 五、验收标准与交付边界

**业务与体验**

- 至少 4/5 用户独立完成角色任务，覆盖桌面、手机、200% 缩放、真实输入法及关键键盘操作。
- 莆仙完整走通导入、独立校对、仲裁、质量判断、编选、交付、接收回执。
- 蒙古语及特殊字符在输入、显示、复制、存储和导出全过程无非预期变化。
- 报告数量与权威记录一致；未知不算零，一致不算正确，下载不算接收。

**正确性与恢复**

- 覆盖断网、重复点击、租约失效、旧草稿、撤权、作业重启、依据变化和交付冲突。
- 丢写、重复提交、越权读取和静默字符变化为零容忍项。
- 恢复目标沿用 **RPO ≤24 小时、RTO ≤60 分钟**；只报告实际数据规模下的测量结果。

**性能**

沿用已有目标：读取 p95≤500ms；领取、提交和仲裁 p95≤800ms、p99≤2s；冷原文可读≤3s；意外 5xx 与超时≤0.1%。

正式容量仍要求独立生成器、20k 条、30 actors、60 分钟×3及对应故障验证。**现有免费资源不能满足时，保留 #400 未验收，不用同机短测替代。**

**免费资源的明确处理规则**

- 没有可用 SMTP：保留管理员恢复路径，邮件自助保持关闭。
- 没有合适异地存储：完成本地备份和隔离恢复，异地保护保持未验收。
- 没有独立容量环境：完成可执行的工程测试，正式容量保持未验收。
- 涉及这些缺口时，交付状态写为“优化完成、受限试点”，不得宣称正式运营验收全部通过。

最终交付四项成果：**版本与能力状态清单、真实批次质量和接收报告、运行及恢复验收记录、按依赖排序的后续优化清单。**代码、实际发布和真实业务验收分别列明。
