# 万语校坊负责人工作指南：从真实问题到可执行 Backlog

> 面向万语校坊第一负责人。目标不是把 GitHub Issue 写得很多，而是持续把真实资料、真实用户和真实交付中的问题变成可执行、可验收的工作。

## 1. 负责人负责什么

负责人对以下事情负责：

- 真实试点怎么安排、当前最重要的问题是什么；
- Epic 是否仍然反映真实目标；
- 哪些问题应该立即修，哪些继续观察，哪些放到 post-SF；
- Leaf Issue 是否足够具体，能交给成员或 Agent 独立完成；
- PR 合并后 Issue 是否及时收口；
- 每周能够说明 `Done / Demo / Blocked / Next / Need Steering Decision`。

负责人不需要亲自实现全部功能，也不需要提前设计半年后的完整产品。

遇到权利/商业/合同、生产数据破坏风险、重大权限变化或对外承诺，再升级 Steering。

## 2. 先从真实问题开始，不从“完整系统应该有什么”开始

推荐循环：

```text
真实资料 / 真实用户
        ↓
观察问题
        ↓
它是否 blocking / 高频 / 高风险？
        ↓
修复 / 继续观察 / post-SF / 不做
        ↓
确实需要产品化
        ↓
形成 Leaf Issue
        ↓
成员 / Agent 实现
        ↓
PR + Evidence
        ↓
回到真实试点
```

典型反例：

```text
以后可能有很多志愿者
→ 人的能力可能不同
→ 所以要 A/B/C
→ 所以要专家角色
→ 所以要抽检
→ 所以要专家升级队列
```

每一步单独看都有道理，但真实用户尚未遇到这些问题时，一次性把整条链都变成春节任务，会让 backlog 膨胀并抢走真正阻塞工作的资源。

正确做法是先保留必要的长期设计；真实试点证明某一环成为瓶颈后，再把它提升到当前 milestone。

## 3. Tracker、Epic、Leaf、PR 分别干什么

```text
Tracker
→ Epic
→ Leaf Issue
→ PR
```

### Tracker

例如 #91。只回答：

- 春节为什么做；
- 有哪几条主线；
- 总体 Gate 和边界是什么；
- 谁是 Accountable Owner。

不要在 Tracker 手抄每个月全部 Issue。Milestone 本身就是时间计划的真源。

### Epic

例如 #93、#95、#96。回答：

- 这条主线解决什么真实问题；
- 什么证据说明它成立；
- 哪些事情明确不属于它。

Epic 可以持续较长时间，不要求一个 PR 关闭。

### Leaf Issue

应该能够独立认领和验收，至少写清：

1. 真实问题；
2. 期望结果；
3. 验收证据；
4. 明确非目标。

Leaf 可以非常技术化。真实复现数据、根因、测试和定量影响都值得保留。

### PR

PR 是一次具体实现，不是新的项目计划。PR 合并后要回看关联 Issue：

- 已完成 → close completed；
- 只完成一部分 → 回填剩余范围；
- 实现证明原假设错误 → 修改 Issue，而不是让正文继续撒谎。

## 4. 春节阶段怎么判断优先级

对真实试点暴露的问题：

- **Blocking**：阻止核心 journey，优先修。
- **高频明显摩擦**：多人反复遇到，优先修。
- **小型低成本改善**：负责人酌情安排。
- **大型新机制**：默认 post-SF，除非真实证据证明必须提前。
- **理论上合理但尚未出现**：记录即可，不要为了完整感立即开发。

“人工可以处理”不是失败。春节阶段允许群聊协调、启动说明、负责人分工和把困难问题交给更合适的人。只有这些人工动作反复成为瓶颈，才值得产品化。

## 5. #93 与 #95 怎么区分

- **#93 看资料**：真实莆仙资料能否正确、可追溯地生产出来。
- **#95 看人**：换成真实校对者操作，这套生产过程还能不能顺利运行。

同一个试点可以同时给两边提供证据，但不要重复开两张内容相同的票。

#95 不在 GitHub 维护个人产量、排行榜或个人绩效。可以记录参与者构成、onboarding 方式、journey、friction 和处置。

## 6. Issue 生命周期

保持简单：

- Open：仍然有真实工作或等待验证；
- Closed / completed：定义的交付已经完成；
- Closed / not planned：需求失效或明确不做；
- `phase:post-SF`：需求仍有效，但春节前无硬 deadline；
- 条件性方案：保持 Open，并写清“什么证据出现才实施”。

不要因为“这轮不做”就关闭有效需求，也不要因为“以后可能有用”就给它当前 milestone。

## 7. Git 与 PR

独立 PR：

```text
feature → main
```

有代码依赖的 PR：

```text
main
└─ A
   └─ B
      └─ C
```

stack 内同步使用 **rebase**，不要反复 `git merge main` 或 `git merge 前序分支`。

优先使用 GitHub stacked PR / `gh stack rebase` + `gh stack push`。需要改写已发布 stack 时使用安全的 force-with-lease。

自动 reviewer 可以正常 APPROVE / COMMENT / REQUEST_CHANGES。人工负责人决定最终什么时候 Merge；如果 non-blocking 问题值得顺手修，继续修即可，旧 Approve 因新 push 失效是正常现象。

## 8. 每周最小维护动作

每周不需要做一次“大规划”。只回答五件事：

- **Done**：真正完成并能展示什么；
- **Demo**：有什么真实证据；
- **Blocked**：什么阻止下一步；
- **Next**：下一周最重要的少数事项；
- **Need Steering Decision**：哪些事情超出负责人权限。

顺手检查：

- 已完成 Issue 是否还开着；
- milestone 是否仍符合真实 deadline；
- post-SF 是否被误当成当前任务；
- 是否出现重复 Leaf；
- PR 是否改变了 Issue 的原假设；
- 是否有人因为“没有任务”而闲置——如果有，先从真实试点和现有 Epic 找可独立交付的 Leaf，而不是凭空造功能。

## 9. 一个判断口诀

遇到“这个功能要不要做”，依次问：

1. **谁真的遇到了？**
2. **它阻止了什么？**
3. **出现了几次？**
4. **人工处理现在够不够？**
5. **最小产品化动作是什么？**
6. **怎么证明做完真的改善了？**

前四个问题答不清时，通常还不应该进入当前开发队列。
